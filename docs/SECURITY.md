# Security model and scope

## Assets and boundaries

Protect the original log bytes, their ordering and attribution to captured records,
the sealed findings, and the trust anchor retained by the investigator. Inputs may
be malformed, oversized, forged or adversarial. The tool treats them as data and
does not execute embedded SQL. Valid syntax is not proof that a trusted PostgreSQL
server generated a record.

The operator controls a private local output directory. Unix evidence permissions
are 0700/0600. On Windows configure equivalent ACLs. The application rejects
symlink evidence files, but portable standard filesystem checks do not provide a
race-proof sandbox against another process able to replace files concurrently.
Do not run against directories writable by adversaries.

## Detection limits

- Default sensitive basenames: `accounts`, `bank_accounts`, `payments`,
  `transactions`, `customers`, `beneficiaries`, `cards`. This is an explicit lab
  policy, not inferred financial data discovery. Adapt policy and tests to your schema.
- No catalog resolution, view expansion, search-path resolution or behavioral model.
- Procedural SQL, computed `set_config`, function bodies, CTE aliases and unusual
  prepared-statement forms may evade or confuse lexical triage. DB900 flags selected
  known coverage gaps, **not all unsupported SQL**. Absence of findings is not a clean bill of health.
- Logs can be disabled, omitted, modified before capture or generated by an
  already compromised server. Hashing cannot recover missing events or attest the host.
- Ordinary `log_statement` records precede execution; duration records are
  completion logging. The tool does not infer committed transaction success or
  authorized intent from either format. Multiple rows are not distinct incidents.
- These log rules do not model transaction fraud, sanctions or identity attribution.
  The separate [transfer module](FINANCIAL-CRIME.md) provides bounded pattern
  screening for human investigation, with its own declared schema and limits.

## Evidence limits

SHA-256 anchoring is integrity checking, not a digital signature. Save the anchor
through a separately protected channel before handing the bundle to another party.
A replacement bundle plus a replacement anchor is outside this guarantee. Collection
authority, custody procedures, clock reliability and legal admissibility are operator
responsibilities; this project does not certify any of them.

Raw and normalized evidence can contain SQL secrets or personal data. Restrict access;
do not upload arbitrary real logs to a public repository. The published fixture is
original synthetic data from an isolated local PostgreSQL instance. ECS exports omit
raw SQL and identities, but timestamps, SQLSTATE and source hashes remain linkable.

No new cloud service, paid resource, bank system or third-party target is used by the
test harness. It requires a trusted local PostgreSQL installation, uses a newly
created private cluster, ignores inherited PG connection settings and stops only
that cluster. The scanner never accepts a database connection string.

## Optional collector boundary

The offline `prepare-elastic` command accepts a strictly typed, bounded ECS
export. It rejects extra/duplicate fields, unsupported schema/policy metadata,
inconsistent IDs and conflicting same-ID documents in one batch before a new
output file becomes visible. These checks enforce shape and consistency, not
provenance: a caller can fabricate a valid claimed source hash and recompute its
ID. Independent source capture and trusted anchors are still necessary.

Filebeat is a separately trusted collector. Its extra host, agent and file-path
metadata is excluded by an explicit allowlist; strict Elasticsearch mappings and
an ingest pipeline provide additional rejection checks. A rejected document must
be investigated through collector metrics/logs, not silently counted as delivered.
Raw collector/server logs can contain rejected input or local paths and must not
be published. Only the sanitized lab result is suitable for public examples.

The integration harness starts its own new loopback-only cluster with a basic
license and no authentication/TLS. This is safe only on a trusted host with the
included synthetic fixture; local users are inside its trust boundary. It must
not be deployed on a shared or untrusted host, exposed on a network interface,
or adapted to real data without an authenticated, authorized deployment design.

The shipped collector uses create-only writes: replayed IDs produce HTTP 409
without replacing existing documents. A conflict response does not distinguish
same-content replay from a changed payload claiming the same ID. Operators need
a separate trusted conflict workflow; duplicate counters are not correctness
attestations. The lab deliberately checks this boundary. Administrators or writers
with different permissions/configuration may still alter the underlying index.

The index is not append-only evidence, a global conflict registry, or proof that
every source event was collected. Keep immutable-by-workflow evidence bundles and
externally trusted digests outside Elasticsearch. No production access-control,
crash-durability or large-volume delivery guarantee is claimed by the small lab.
